# Reflect Life Insight Demo Design

## Goal

완성된 추억 영상 다음 단계에서 사용자가 최근 기억의 변화를 돌아볼 수 있도록, 같은 웹 화면 안에 `Reflect` 경험을 추가한다. 발표용 데모이므로 실제 회원 계정, 장기 데이터베이스, 얼굴 인식은 만들지 않는다. 대신 브라우저에 저장한 데모 기억과 방금 만든 영상의 정보를 사용해 통계 근거가 있는 한 문단의 회고를 생성한다.

## User Experience

1. 사용자가 기존 흐름으로 영상을 업로드하고 완성 영상을 확인한다.
2. 완성 화면의 `한 달의 기억 돌아보기` 버튼을 누른다.
3. 화면 이동 없이 분석 중 상태를 보여준다.
4. 분석이 끝나면 같은 화면에 다음 내용을 표시한다.
   - `Life Insight`: 최근 기억에서 관찰한 변화 한 문장
   - `Evidence`: 그 문장을 뒷받침하는 숫자 또는 기간 비교
   - `Tomorrow`: 부담 없이 실행할 수 있는 제안형 질문
   - `Favorite Memory`: 분석과 연결되는 대표 기억 한 장
5. 사용자는 완성 영상을 다시 보거나 새 영상 만들기로 돌아갈 수 있다.

## Scope

### Included

- 최근 28일을 이전 14일과 최근 14일로 나눠 활동 변화를 계산한다.
- 최초 실행 시 발표용 기억 데이터를 브라우저 저장소에 넣는다.
- 방금 완성된 영상은 작업 ID를 기준으로 중복 없이 기억 목록에 추가한다.
- 서버는 계산된 근거만 전달받아 자연스러운 회고 문장을 생성한다.
- LLM 호출이 실패하거나 응답 형식이 잘못되어도 코드 기반 기본 결과를 반환한다.
- 모든 Reflect 상태는 기존 `/create` 화면 안에서 전환한다.

### Excluded

- 로그인, 회원가입, 사용자별 서버 저장소
- 얼굴·인물 자동 식별 및 관계 추론
- 벡터 데이터베이스나 장기 검색
- 의학적·심리학적 진단
- 실시간 스트리밍 응답
- 여러 달에 걸친 실제 생활 패턴 분석

## Memory Data Model

브라우저는 `my-tiny-cute-video-memories-v1` 키로 다음 형태의 배열을 저장한다.

```ts
interface MemoryRecord {
  id: string;
  occurredAt: string;
  title: string;
  summary: string;
  people: string[];
  places: string[];
  activities: string[];
  categories: Array<"friends" | "family" | "outdoor" | "travel" | "food" | "daily">;
  mood: "warm" | "joyful" | "calm" | "nostalgic";
  importance: number;
  thumbnail?: string;
  sourceJobId?: string;
}
```

`importance`는 1부터 5까지의 정수다. 데모 데이터의 날짜는 실행 시점을 기준으로 생성해 발표 날짜가 바뀌어도 최근 28일 비교가 유지되게 한다. 외부 이미지 주소에 의존하지 않고 기존 로컬 이미지나 텍스트형 폴라로이드 카드를 사용한다.

## Deterministic Analysis

서버의 순수 함수가 먼저 다음 순서로 분석한다.

1. 유효한 날짜이며 최근 28일 안에 있는 기억만 사용한다.
2. 이전 14일과 최근 14일의 카테고리별 기억 수를 계산한다.
3. 이전 기간에 한 번 이상 있었고 최근 기간에서 가장 많이 감소한 카테고리를 선택한다.
4. 감소가 없으면 최근 기간에서 가장 자주 등장한 카테고리를 선택한다.
5. 선택한 카테고리와 관련된 기억 중 중요도가 가장 높고 날짜가 최신인 항목을 대표 기억으로 고른다.
6. 비교 수치, 기간, 선택 카테고리를 구조화된 근거로 만든다.

이 계산은 LLM에 맡기지 않는다. 따라서 화면에 표시되는 수치와 대표 기억은 항상 입력 데이터에서 재현할 수 있다.

## LLM Contract

프런트엔드는 `POST /reflect`에 최대 60개의 `MemoryRecord`를 보낸다. 서버는 문자열 길이, 배열 길이, 날짜, 중요도 범위를 검증한 후 통계를 계산한다.

LLM에는 원본 영상이나 불필요한 개인정보 대신 다음의 압축된 근거만 전달한다.

- 비교 기간
- 선택 카테고리
- 이전 기간 횟수와 최근 기간 횟수
- 대표 기억의 제목과 요약

시스템 지침은 다음 원칙을 강제한다.

- 제공된 근거 밖의 사실을 만들지 않는다.
- 감정 상태, 건강, 인간관계를 진단하지 않는다.
- 비난하거나 단정하지 않고 따뜻한 한국어를 사용한다.
- 제안은 질문형 한 문장으로 작성한다.
- 데이터가 부족하면 변화가 확인되지 않았다고 명시한다.

응답 JSON은 다음 형태다.

```ts
interface ReflectionResult {
  observation: string;
  evidence: string[];
  suggestion: string;
  featuredMemoryId: string;
  source: "llm" | "fallback";
}
```

서버는 JSON 파싱과 필수 필드 검증에 실패하거나 LLM 호출에서 오류가 발생하면 같은 통계를 이용한 코드 기반 한국어 문장을 `source: "fallback"`으로 반환한다. 따라서 외부 모델 장애가 Reflect 화면 전체의 실패로 이어지지 않는다.

## Components and Data Flow

- `demo-memories`: 상대 날짜를 사용하는 발표용 기억 목록을 만든다.
- `memory-store`: 브라우저 저장소 초기화, 조회, 완성 작업의 중복 없는 추가를 담당한다.
- `reflection types`: 프런트엔드와 서버 계약에 대응하는 타입을 정의한다.
- `reflection analysis`: 기간 분할, 카테고리 비교, 대표 기억 선택, 기본 응답을 담당하는 서버 순수 함수다.
- `POST /reflect`: 입력 검증, 순수 분석 호출, LLM 문장 생성과 대체 응답 선택을 담당한다.
- `ReflectPanel`: 로딩, 결과, 재시도 상태를 표현하고 기존 추억 회상 디자인을 이어받는다.
- `create route`: 영상 완성, Reflect 분석, 결과 표시 간의 화면 상태만 조정한다.

데이터 흐름은 `브라우저 기억 목록 → /reflect → 통계 계산 → LLM 문장화 또는 기본 문장 → 같은 화면 결과 표시` 순서다.

## Error Handling

- 브라우저 저장 데이터가 손상되면 해당 값을 버리고 데모 기억으로 다시 초기화한다.
- 서버는 잘못된 요청에 400 응답을 반환한다.
- 유효한 기억이 없으면 `분석할 기억이 아직 충분하지 않아요`라는 기본 결과를 반환한다.
- LLM 오류는 서버 내부에서 대체 결과로 흡수하고 200 응답을 유지한다.
- 네트워크 자체가 실패하면 화면에 재시도 버튼과 기존 완성 영상으로 돌아가는 버튼을 함께 표시한다.
- 재시도와 결과 표시는 페이지 이동이나 새로고침을 일으키지 않는다.

## Privacy and Safety

발표용 데모 기억은 브라우저에만 저장한다. 서버는 Reflect 요청을 영구 저장하지 않는다. LLM에는 영상 파일, 얼굴 이미지, 파일명 전체를 전달하지 않고 통계와 짧은 텍스트만 전달한다. 출력은 생활 패턴에 대한 가벼운 관찰과 제안에 한정한다.

## Testing

- 서버 단위 테스트로 기간 경계, 감소 카테고리 선택, 변화가 없는 경우, 대표 기억 선택, 빈 입력 기본 응답을 검증한다.
- API 테스트 가능한 순수 경계를 유지해 LLM JSON 검증과 대체 응답을 독립적으로 검증한다.
- 브라우저 테스트에서 완료된 영상 뒤 Reflect 버튼을 누르고, `/reflect` 응답을 받아 같은 `/create` 화면에 관찰·근거·제안·대표 기억이 표시되는지 확인한다.
- 네트워크 실패 시 재시도 UI가 표시되고 기존 완성 영상으로 복귀 가능한지 확인한다.
- 최종 검증은 Python 테스트, 프런트엔드 테스트, 타입 검사, 프로덕션 빌드를 모두 실행한다.

## Deployment

서버 API 이미지에는 기존 웹 API 의존성에 LLM SDK를 추가하고, 이미 연결된 서버 비밀키에서 API 키를 읽는다. 서버 배포와 프런트엔드 배포는 코드 검증 후 각각 수행한다. Git 원격 반영이나 실제 배포는 사용자의 별도 승인 없이 실행하지 않는다.
